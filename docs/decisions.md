# Decisions

Short numbered log of decisions that shape the code. Add a line when one is made; never rewrite an old one, add a new one that supersedes it.

- **D1 (2026-11-02) Public core, private production.** This repo is the open-source provenance core. Production-specific CMS work (a client's tour, scripts, scene editors) lives in a private downstream repo that merges `main` from here and never pushes back. Nothing in this repo names a client or production.
- **D2 (2026-11-02) Timeline format: xmeml first.** The first timeline parser reads FCP 7 XML (`<xmeml>`), which Premiere exports as "Final Cut Pro XML" and Resolve exports too. It is documented and carries exactly the data needed. FCPXML is a later registry module. The `.prproj` project file is readable but undocumented and version-dependent; a reader is only considered if creators resist the export step and no NLE-side helper exists.
- **D3 (2026-11-02) Origin-class vocabulary.** One class per asset, stored and user-confirmable: `captured_signed`, `captured`, `archival`, `archival_enhanced`, `generated`, `composited`, `unknown`. Proposed by extraction, confirmed by the user; an unconfirmed class counts as a missing enrichment field.
- **D4 (2026-11-02) Relationships as polymorphic pairs.** `asset_relationships` carries `(parent_asset_type, parent_asset_id)` and `(child_asset_type, child_asset_id)` across the three asset tables rather than a unified `asset_refs` table. Smaller blast radius; the later modification chain is a new table pointing at relationship rows.
- **D5 (2026-11-02) Neutral assertion namespace.** Custom C2PA assertions written by this tool use `org.provenancetracker.*`, documented with a committed JSON schema. Vendor namespaces belong in downstream forks.
- **D6 (2026-11-02) Idempotent migrations.** Every migration after `0003` uses `IF NOT EXISTS` on `CREATE TABLE` and `ADD COLUMN`, so a downstream fork with its own migrations can merge public `main` without a failing migrator. The one allowed hand edit of generated SQL is adding those clauses, in the generating commit.
- **D7 (2026-11-02) Overlays reported separately.** The default screen-time breakdown is computed on the primary picture track only. Overlay tracks are stored, classified and reported separately; there is no area threshold in this phase.
- **D8 (2026-11-02) Archival triage stays downstream for now.** The stop-assignment and selects workflow built for one production is not ported to the public repo; a generic "collections" feature may replace it later.
- **D9 (2026-11-03) Renovate for dependency updates, majors by approval.** Renovate replaces Dependabot version updates (`renovate.json5`). Minor and patch updates arrive as one weekly grouped PR; major updates wait on the Dependency Dashboard issue until approved, because a major is planned work, not a merge-button decision. Dependabot does not run on repos nobody has touched for 90 days, and the dashboard issue is the catch-up list when a dormant repo is reopened. Dependabot security alerts and the CI `npm run audit` step stay as the vulnerability signal.
- **D10 (2026-11-03) Outputs and the composed view; supersedes D7 for the headline.** A produced asset flagged `is_output` is a finished edit (set on timeline import, on import of a file whose credentials list ingredients, or by hand) and lives under an Outputs section, separate from the source material. Its headline is the composition (`src/server/lib/timeline/compose.js`): for every moment, what is on screen and what is audible across all tracks, as `single`, `mixed` (two or more origin classes at once, drawn as stripes and counted as its own bucket) or `gap`. Percentages derive from those intervals, so strip and numbers cannot disagree. The per-track tallies from D7 stay in the stored breakdown for the record but are not the headline. The per-clip class override is no longer offered in the UI: an origin class describes the material, so a change made from a timeline row sets the asset's class, with an optional note (`origin_class_note`) that the output manifest will carry. A manual match that agrees with the file by path or hash is recorded with that evidence, not as `manual`.
- **D11 (2026-11-11) Origin classes are IPTC digital source types; colour is the spectrum position. Supersedes D3's vocabulary.** An asset's `origin_class` is an IPTC Digital Source Type code, the term a C2PA manifest carries as `digitalSourceType`, or `unknown`. Nothing is translated on the way in or out; the classifier keeps what a file declares and corrects only the known misuses (an export stamped with a single-asset edit code is a composite; an `empty` canvas filled by a generative model is AI-generated). All 17 active terms are accepted, a short list is offered first, and retired terms are read as their successors. The definitions and the reasoning are in `docs/vocabulary.md`; the code is `src/shared/origin-vocabulary.js`, shared by server and client. Three facts that D3 baked into class names are attributes: who signed the file (`signed_by`: device, tool or creator, with `signer_name`), whether it is from an archive (the asset's table), and `ai_assisted` (an AI model wrote the instructions, such as code, and an ordinary program made the pixels; IPTC has no term for this). Colour, mixing on the composition strip and the headline numbers follow the spectrum position (camera-captured, digital with no AI, AI-assisted, hybrid, fully synthetic, unknown), which several classes share; the six colours are CSS custom properties (`--pt-origin-*`). A finished edit's class is worked out from what is in it. Data migrations like the one that renamed the stored classes are hand-written files made with `drizzle-kit generate --custom`, dry-run inside a rolled-back transaction first; generated schema migrations are still only edited to add `IF NOT EXISTS`.
- **D12 (2026-11-13) Track in place; signed copies are records, not repointed rows.** Scan-folder and file-path imports can record a file where it already lives (`in_place`) instead of copying it into managed storage; this is the default for produced media, whose files already sit in an edit project that links to them by path. The copy-into-storage default came from the image library, where uploads and URL downloads have no other home, and it stays for those. A file tracked in place is never moved, renamed or deleted by the tracker, and an import that asks to delete originals is refused. Because other tools can change it, the integrity check reports in-place files that are missing or whose size differs from the one recorded at import. Signing (4c) writes a new file and records it in `signatures`; the asset row keeps the original's path and hash, so timelines still match the file the editor uses.
- **D13 (2026-11-13) Sidecars for source assets, embedded only for deliverables.** Signing a source asset at ingest writes its manifest to a `.c2pa` sidecar beside the file, named like it (`take.mp4` gets `take.c2pa`), which is where C2PA readers look; the file is never written, so nothing is duplicated and edit projects keep their links. Signing again archives the previous sidecar as `<name>.v<N>.c2pa`, and a `.c2pa` the tracker did not write is never replaced. Only a deliverable (a signed output) gets its manifest embedded, in a new `<name>.signed.v<N>.<ext>`, because platforms and viewers read only what is inside the file. A file that already carries embedded credentials is not signed at ingest: c2patool can only sidecar-sign it against a copy with those credentials stripped, which then does not match the original, and its own credentials are already its provenance. c2patool's ingredient reader ignores sidecars, so the signer attaches an ingredient's sidecar as its manifest store itself; a sidecar-signed WAV keeps its credentials inside the signed output. Measured on a 1.6 GB Pixel take: 14 s, a 13.5 KB sidecar (c2patool writes a temporary copy of the asset, deleted straight away).
- **D14 (2026-11-21) Catalog storage: plain SQL on `node:sqlite`, confirmed.** Spike on Node 24.13.1 (SQLite 3.51.2) on the three local SSDs that hold media: WAL, foreign keys, transactions, triggers that refuse UPDATE and DELETE on append-only tables, a second connection, the online `backup()` API and write-to-temp-then-rename all work. Node prints one experimental warning per process; the app silences that one warning by name, not all warnings. SQLite folds case for ASCII only, so plain `LIKE` misses accented and upper-case matches ("pena" finds neither "Peña" nor "PEÑA"). Search uses a column the app writes already folded (Unicode decomposition, combining marks removed, lower-cased) for field filters, and FTS5 with `tokenize='unicode61 remove_diacritics 2'` (present in Node's build) for free text; which field gets which is settled in the catalog phase. A catalog inside a cloud-sync folder (Google Drive, Dropbox, OneDrive) can be corrupted by the sync client, so the app refuses or warns when a project folder is inside one. `better-sqlite3` is not needed.
- **D15 (2026-11-21) Engine: the C2PA library by default; c2patool is not a validator of camera files.** `@contentauth/c2pa-node` 0.10.0 and 0.12.1 load on Windows, read a Pixel clip as valid and, with the official C2PA trust list (`c2pa-org/conformance-public`, `trust-list/C2PA-TRUST-LIST.pem`), as trusted; sign an MP4 with ingredients and a custom assertion; keep an ingredient's own manifest inside the signed file; and accept a signing callback, so the library never needs to hold the key (the seam for a keychain, hardware token or remote signer). Every c2patool release up to 0.27.23 (built on c2pa-rs 0.90.23) reports genuine Pixel video as invalid (`assertion.bmffHash.mismatch`), where the library, on c2pa-rs 0.91 and later, reads it correctly; until a c2patool built on 0.91 or later exists, c2patool may sign and may read the tool's own outputs, and never decides whether a camera file is valid. Three constraints for the signing phase: the library's install script downloads its native binary without a checksum check, so the binary is fetched by the project at a pinned version with a recorded checksum and supplied through `SKIP_BINARY_DOWNLOAD` and `C2PA_LIBRARY_PATH`; the library wants the key as PKCS#8 (the dev key is SEC1 and is converted in memory); and neither the library's native binary nor c2patool is code-signed, which Smart App Control blocks and a downloadable app has to solve.
- **D16 (2026-11-21) TypeScript runs directly on Node; erasable syntax only.** Node 24 runs `.ts` server and package files with no build step and no warning, keeping line numbers. It refuses `enum`, `namespace`, constructor parameter properties, decorators and extensionless imports, so the codebase uses none of them: imports name the `.ts` file, and `tsconfig.json` sets `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, `rewriteRelativeImportExtensions` and `noEmit`, so the type check in CI reports exactly what Node would refuse. A workspace package that exports `.ts` files works through `node_modules` because Node follows the link to the real folder; `--preserve-symlinks` breaks this and is never used. TypeScript 6.0 is the version, because typescript-eslint supports releases below 6.1 only; TypeScript 7 (the native compiler) is a planned major once it does. Worktrees currently link the whole `node_modules` to the main checkout, which would load the main checkout's packages instead of the worktree's; the packages phase changes the worktree setup. The client is built by Vite, which handles its TypeScript itself.
- **D17 (2026-11-21) Screen time travels as time ranges on `c2pa.placed`.** C2PA 2.4 (section 18.15.4.6) lets an action name the part of an asset it applies to through `changes`, a list of regions of interest; a temporal region is `{"type": "temporal", "time": {"type": "npt", "start": "5", "end": "12"}}`, start inclusive, end exclusive. Section 18.16.3 requires a `c2pa.placed` action for each `componentOf` ingredient. The manifest builder writes one `c2pa.placed` action per placement on the timeline, linked to its ingredient and carrying that placement's range, so a clip used twice has two actions; the specification does not say how a reader should combine several ranges on one action, so the builder does not rely on it. The library and c2patool both keep the ranges and the ingredient links through signing and reading. Two public verifiers were tried on a synthetic signed file: both accept it (valid, signer untrusted as expected for the dev certificate), c2paviewer.com keeps the ranges and links in its full report, and neither shows the ranges in its readable view (contentcredentials.org lists the placements as "Imported"). So the ranges are for machine readers and the evidence trail; the project's own viewer is where a person sees them. Neither verifier had a picture to show, because the signed file carried no thumbnail of its own: the signing phase adds a poster frame as the claim thumbnail of every signed deliverable. The custom `org.provenancetracker.creator_statement` assertion stays, since it carries what the standard actions cannot (origin class, who set it, the composed breakdown).
- **D18 (2026-11-21) The name stays; the namespace sits on a domain the project holds.** The project is called Provenance Tracker and is maintained by Origen Story. `provenancetracker.org` is registered for it, so the `org.provenancetracker.*` labels of D5 are the reverse of a domain the project controls, as C2PA expects of a custom label, and they do not change. Spelling: "Provenance Tracker" in prose; `provenance-tracker` for the repository; `provenancetracker`, one word, wherever a machine reads the name (the domain, the assertion labels, the npm scope `@provenancetracker`, and the `.provenancetracker/` folder that will hold a project's catalog). The domain forwards to the repository for now. It will serve the export schema and the specification at stable addresses; the schema's `$id` moves there at that point and stays a GitHub address until then, so no published identifier points at a page that does not exist.
- **D19 (2026-11-21) Formatting and lint are tools' work, not review topics.** Prettier formats every file with its defaults plus one change, tabs instead of spaces: each developer sets how wide a tab looks in their own editor, which matters to people working with large fonts or screen magnifiers (the reasoning is in `prettier.config.js`; YAML keeps spaces, which it requires). ESLint runs its recommended rules and typescript-eslint's on every file, JavaScript included, with Prettier's conflicting rules switched off; type-aware rules wait until files are TypeScript. TypeScript 6.0 type-checks with `allowJs` and without `checkJs`, so existing JavaScript is read but checked only once converted (D16). CI runs all three in a `lint` job that `main` requires. The one reformatting commit is listed in `.git-blame-ignore-revs`, so pull requests are merged with merge commits, never squashed, to keep that commit's id.
- **D20 (2026-11-21) Dependencies: few, exact, aged, checksummed.** A signing tool is a target for tampered packages, so the rules in `docs/dependencies.md` apply: a new runtime dependency needs a stated reason in this log; `package.json` names exact versions and `.npmrc` sets `save-exact`; releases are taken at least 14 days after publication, by Renovate and by hand alike; and helper programs that do not come from npm are installed by `npm run tools:fetch` at the version and SHA-256 recorded in `scripts/lib/pinned-tools.mjs`, refusing any download that does not match. c2patool is pinned at 0.27.1, the version already in use (a newer release would not fix the Pixel misreading in D15). The two PNG packages were removed, since nothing imported them. Dependencies already scheduled to go leave when the roadmap reaches them, as listed in `docs/dependencies.md`.
- **D21 (2026-11-21) Extractors return observations.** Every reader of a file (ExifTool, the two C2PA readers, the PNG text reader) returns the same shape, defined in `src/server/lib/extraction/observation.ts`: `kind`, `extractor` and `version` (the program that read the file, so a later upgrade can be told apart from a change in the file), `status` (`ok`, `absent`, `unreadable`, `unavailable`, so "nothing there" is never confused with "could not look"), the full `data` read, `error`, `warnings` and, for C2PA, the reader's `validation` (its state, failure codes and raw results). The data is made safe to store as JSON without losing evidence: binary fields such as embedded thumbnails become their size and SHA-256 (a Firefly image's manifest store goes from 665 KB to 2.4 KB), and ExifTool's dates keep their raw text. ExifTool tags that describe where a file sits rather than what it contains (file name, folder, file-system dates, permissions) are left out, since they differ between two copies of the same bytes and `FileAccessDate` changes on every read; they belong to a file's location in the catalog. When the C2PA fast path fails and c2patool reads the file, both attempts are kept, so neither reader's verdict is lost (on a Pixel clip today: c2pa-node 0.5.26 cannot decode it, and c2patool reports it invalid, D15). The catalog stores observations as rows that never change. Until then the current app keeps storing the summaries it stored before, derived from observations by pure functions; the one addition is `validation` on `c2paJson`, which was computed and discarded before. The full EXIF tag set is not stored by the current app, because its pages display `exifJson` entries one by one and cannot show object values. Writing this found and fixed a bug in the PNG reader: uncompressed iTXt text was stored with a stray zero byte at the start (the compression flag and method are single bytes, not terminated strings), and compressed iTXt is now read.
- **D22 (2026-11-21) CodeQL alerts are fixed or dismissed with a reason; none are left unanswered.** The first full scan of `main` found 30 alerts. Three were fixed. Image downloads (URL import and the parked Wikimedia queue) now go only to public addresses: `src/server/lib/core/public-url.ts` allows http and https without credentials, refuses a host if any address it resolves to is on this machine or a local or reserved network, and re-checks every redirect itself (DNS rebinding is the stated gap, `docs/threat-model.md`). The Gigapixel file-name match uses `indexOf` instead of a regex whose time grew with the square of the name's length. Commons HTML fields are stripped of tags until none are left. Two kinds are dismissed as "won't fix", each with its reason recorded in `docs/threat-model.md`: `js/path-injection` (reading a path you choose is what the tool is for, and it is fixed properly when paths are confined to a project's media folders in the catalog phase) and `js/missing-rate-limiting` (one user, local-only API). OpenSSF Scorecard checks, which share the Security tab, are left open. A pull-request scan reports only the lines that pull request changes, so the alerts on `main` are checked after each merge, not inferred from a green pull request.
- **D23 (2026-11-21) One opaque asset reference in the pure modules.** Matching, composition, the breakdown, the manifest builder and auto-linking name an asset by its `ref` and never look inside it; `(type, id)` pairs and the builder's `assetKey()` are gone from them. Today the old app makes a ref from its table and row id (`src/server/lib/core/asset-ref.ts`), as the same text `assetKey()` produced, so ingredient order and labels cannot change; the catalog's stable asset id becomes the ref in the catalog phase, and nothing in the pure modules changes then. The old app converts at its edges: index builders add refs, timeline segments are stored in the same columns as before, and a breakdown cached before refs existed gets them added as it is read, with no recompute and no write. Checked against the real database, read only: every output's manifest (three outputs, 13 to 30 ingredients) built byte-identical before and after, both from the cached breakdowns and from breakdowns recomputed in memory. That check is the first rehearsal of the byte-equal export required at the migration.
- **D24 (2026-11-21) The pure modules are a package; the app moves later.** The modules with no IO live in `packages/core` as `@provenancetracker/core`, an npm workspace of this repository, with their tests and fixtures beside them (`packages/core/test/`): the origin vocabulary, the asset ref, the observation shape, the platform parsers and their dispatch, video tags, the manifest builder, public export and report verification, the classifier, auto-linking, and the timeline formats, matching, composition and breakdown. The app and the React client import them by package name; inside the package imports are relative, and a lint rule refuses any import of the app, the database or HTTP from it. Files moved with `git mv`, so their history follows them. The roadmap put the app in `packages/app` at the same time; it stays at the repository root until the app cutover instead, because moving it now would mean editing the guard hook and deny rule that protect `src/server/db/migrations/`, a folder the cutover deletes. `public-viewer/` also stays where it is until it is confirmed that nothing outside this repository reads it from that path. Worktrees no longer share the main checkout's `node_modules`: the workspace link inside it would load the main checkout's `packages/core` (D16), so a worktree that runs code runs `npm ci` first.
- **D25 (2026-11-21) The formats others rely on live in `spec/`, each with a schema; the creator statement schema exists at last.** `spec/` holds a README listing each format, its version and its schema, and the rule for changing one: anything a current reader could misread is a new version with a new schema file, and old schema files stay. The public export schema moved there from `schemas/` (its `$id` follows to the new GitHub path; published exports do not carry the address, so nothing breaks). `spec/creator-statement.v3.schema.json` is the schema D5 promised for the `org.provenancetracker.creator_statement` assertion and that was never written. It forbids undescribed fields, and tests validate the builder's statement, a statement with an unresolved nested sequence and the assertion placed in a built manifest against it, plus a check that the schema's version is the builder's. When it was written it was also checked against the three statements already signed into the project's films (28 and 29 ingredients each): all valid. The vocabulary reference stays at `docs/vocabulary.md`, linked from `spec/`.
- **D26 (2026-11-21) The catalog format: one SQLite file per project, versioned, with records that cannot be edited.** A catalog is `<project>/.provenancetracker/catalog.sqlite`, marked as one by `PRAGMA application_id` 1349932146 ('PvTr') and carrying its format number in `PRAGMA user_version`. Format 1's SQL is `packages/core/src/catalog/schema-v1.ts`, published as `spec/catalog/catalog.v1.sql`, which run on its own in the sqlite3 shell makes a working catalog. Tables are STRICT (SQLite refuses a value of the wrong type), JSON columns are checked valid, and each connection turns foreign keys on and trusted schema off, so a catalog someone else made cannot run functions through its own triggers. Records of what happened (runs, contents, observations, history, statements, signatures) are guarded by triggers that refuse updates and deletes; a run may record its ending once; a content may move to another asset but its hash and size are fixed; assets are never deleted, only marked removed. Current values are ordinary rows; the function that writes a human edit with its history row is step 2. Changes from the roadmap's table list: one full SHA-256 per content and no quick fingerprint (hashing ran at about 1.2 GB/s on 450 MB clips, so even large projects hash in minutes, and a second identity that can be wrong is not worth that); technical values (duration, codecs, size in pixels) stay in observations rather than being copied into columns; credits record who made an asset apart from who they acted for and who says so (CAWG's delegation proposal, issue #286, is open and not adopted; identity assertion 1.3 is current); matching is per timeline source, so every clip of a file follows one match; file names and titles get accent-folded columns for filters, and titles, notes, captions, credits and statements get FTS5 search (D14). `project_config`, `manifests` and the Wikimedia search tables are not carried. Compatibility rules: an older catalog is upgraded one step at a time, each step in its own transaction with an upgrade run recording where the caller saved its copy of the file beforehand; a newer catalog is refused in words and left unchanged; another program's database is called foreign and refused. Each format keeps a sample catalog with a row in every table in `packages/core/test/fixtures/catalog/`, and the tests upgrade every sample on every change and require the result to match a new catalog's schema exactly. Format 1 is a draft (`CATALOG_FORMAT_STATUS`) until the first real catalog is written in the Postgres migration (Phase 5): until then its SQL may change and the sample is rebuilt by `npm run catalog:write`; after that it never changes, and a change is format 2. Core runs SQL on a database it is handed and never opens a file; opening, WAL mode and the copy before an upgrade belong to `@provenancetracker/core-node` (step 3).
- **D27 (2026-11-21) One way to change a human-editable value, and a check that nothing went around it.** `packages/core/src/catalog/fields.ts` lists, table by table, the fields a person (or a tool acting as one) may change, with their types; everything else is written once by the code that creates the row, or derived (accent-folded copies, `updated_at`). `catalog/edit.ts` is the only writer of those fields: `createRow`, `editRow`, `removeRow` and `setMeta` each change the row and add a history entry per field that really changed, in one transaction, and say who did it (a person by name; a tool by name and version, with its run; or `legacy`, for a value carried from an older system that cannot say whether a person typed it). A value set to what it already is records nothing. History stores each value's JSON (a boolean as true or false, a JSON field as its value), with null meaning "row created" in the old value and "row removed" in the new one. Assets, contents and roots are never deleted; rows that may be (credits, links, generation settings, timelines with their sources and clips) record each field's last value first, and those tables use AUTOINCREMENT so a removed row's id never comes back to mean something else. `catalog/verify.ts` checks the other way round: every editable field equals its latest history entry, or its column's default if it has never been changed; a row that is gone has a history entry saying so; folded copies match; required project settings exist; plus SQLite's own integrity and foreign-key checks. The defaults come from the catalog itself (`PRAGMA table_info`), so they are never written down twice. Every catalog test opens its catalogs through `catalogsForTests()`, which runs the check after each test, so a test that writes around `edit.ts` fails unless it says it means to; with history writing switched off in `editRow`, 38 tests failed. `catalog/runs.ts` opens a run before its work and seals it at the end. Format 1 stays a draft (D26), so the sample catalog is now written through these functions and passes the check.
