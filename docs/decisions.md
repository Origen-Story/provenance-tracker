# Decisions

Short numbered log of decisions that shape the code. Add a line when one is made; never rewrite an old one, add a new one that supersedes it.

- **D1 (2026-11-02) Public core, private production.** This repo is the open-source provenance core. Production-specific CMS work (a client's tour, scripts, scene editors) lives in a private downstream repo that merges `main` from here and never pushes back. Nothing in this repo names a client or production.
- **D2 (2026-11-02) Timeline format: xmeml first.** The first timeline parser reads FCP 7 XML (`<xmeml>`), which Premiere exports as "Final Cut Pro XML" and Resolve exports too. It is documented and carries exactly the data needed. FCPXML is a later registry module. The `.prproj` project file is readable but undocumented and version-dependent; a reader is only considered if creators resist the export step and no NLE-side helper exists.
- **D3 (2026-11-02) Origin-class vocabulary.** One class per asset, stored and user-confirmable: `captured_signed`, `captured`, `archival`, `archival_enhanced`, `generated`, `composited`, `unknown`. Proposed by extraction, confirmed by the user; an unconfirmed class counts as a missing enrichment field.
- **D4 (2026-11-02) Relationships as polymorphic pairs.** `asset_relationships` carries `(parent_asset_type, parent_asset_id)` and `(child_asset_type, child_asset_id)` across the three asset tables rather than a unified `asset_refs` table. Smaller blast radius; the later modification chain is a new table pointing at relationship rows.
- **D5 (2026-11-02) Neutral assertion namespace.** Custom C2PA assertions written by this tool use `org.provenancetracker.*`, documented with a committed JSON schema. Vendor namespaces belong in downstream forks.
- **D6 (2026-11-02) Idempotent migrations.** Every migration after `0003` uses `IF NOT EXISTS` on `CREATE TABLE` and `ADD COLUMN`, so a downstream fork with its own migrations can merge public `main` without a failing migrator. The one allowed hand edit of generated SQL is adding those clauses, in the generating commit.
- **D7 (2026-11-02) Overlays reported separately.** The default screen-time breakdown is computed on the primary picture track only. Overlay tracks are stored, classified and reported separately; there is no area threshold in this phase.
- **D8 (2026-11-02) Archival triage stays downstream for now.** The stop-assignment and selects workflow built for one production is not ported to the public repo; a generic "collections" feature may replace it later.
- **D9 (2026-11-03) Renovate for dependency updates, majors by approval.** Renovate replaces Dependabot version updates (`renovate.json5`). Minor and patch updates arrive as one weekly grouped PR; major updates wait on the Dependency Dashboard issue until approved, because a major is planned work, not a merge-button decision. Dependabot does not run on repos nobody has touched for 90 days, and the dashboard issue is the catch-up list when a dormant repo is reopened. Dependabot security alerts and the CI `npm run audit` step stay as the vulnerability signal.
- **D10 (2026-11-03) Outputs and the composed view; supersedes D7 for the headline.** A produced asset flagged `is_output` is a finished edit (set on timeline import, on import of a file whose credentials list ingredients, or by hand) and lives under an Outputs section, separate from the source material. Its headline is the composition (`src/server/lib/timeline/compose.js`): for every moment, what is on screen and what is audible across all tracks, as `single`, `mixed` (two or more origin classes at once, drawn as stripes and counted as its own bucket) or `gap`. Percentages derive from those intervals, so strip and numbers cannot disagree. The per-track tallies from D7 stay in the stored breakdown for the record but are not the headline. The per-clip class override is no longer offered in the UI: an origin class describes the material, so a change made from a timeline row sets the asset's class, with an optional note (`origin_class_note`) that the output manifest will carry. A manual match that agrees with the file by path or hash is recorded with that evidence, not as `manual`.
- **D11 (2026-11-11) Origin classes are IPTC digital source types; colour is the spectrum position. Supersedes D3's vocabulary.** An asset's `origin_class` is an IPTC Digital Source Type code, the term a C2PA manifest carries as `digitalSourceType`, or `unknown`. Nothing is translated on the way in or out; the classifier keeps what a file declares and corrects only the known misuses (an export stamped with a single-asset edit code is a composite; an `empty` canvas filled by a generative model is AI-generated). All 17 active terms are accepted, a short list is offered first, and retired terms are read as their successors. The definitions and the reasoning are in `docs/vocabulary.md`; the code is `src/shared/origin-vocabulary.js`, shared by server and client. Three facts that D3 baked into class names are attributes: who signed the file (`signed_by`: device, tool or creator, with `signer_name`), whether it is from an archive (the asset's table), and `ai_assisted` (an AI model wrote the instructions, such as code, and an ordinary program made the pixels; IPTC has no term for this). Colour, mixing on the composition strip and the headline numbers follow the spectrum position (camera-captured, digital with no AI, AI-assisted, hybrid, fully synthetic, unknown), which several classes share; the six colours are CSS custom properties (`--pt-origin-*`). A finished edit's class is worked out from what is in it. Data migrations like the one that renamed the stored classes are hand-written files made with `drizzle-kit generate --custom`, dry-run inside a rolled-back transaction first; generated schema migrations are still only edited to add `IF NOT EXISTS`.
- **D12 (2026-11-13) Track in place; signed copies are records, not repointed rows.** Scan-folder and file-path imports can record a file where it already lives (`in_place`) instead of copying it into managed storage; this is the default for produced media, whose files already sit in an edit project that links to them by path. The copy-into-storage default came from the image library, where uploads and URL downloads have no other home, and it stays for those. A file tracked in place is never moved, renamed or deleted by the tracker, and an import that asks to delete originals is refused. Because other tools can change it, the integrity check reports in-place files that are missing or whose size differs from the one recorded at import. Signing (4c) writes a new file and records it in `signatures`; the asset row keeps the original's path and hash, so timelines still match the file the editor uses.
- **D13 (2026-11-13) Sidecars for source assets, embedded only for deliverables.** Signing a source asset at ingest writes its manifest to a `.c2pa` sidecar beside the file, named like it (`take.mp4` gets `take.c2pa`), which is where C2PA readers look; the file is never written, so nothing is duplicated and edit projects keep their links. Signing again archives the previous sidecar as `<name>.v<N>.c2pa`, and a `.c2pa` the tracker did not write is never replaced. Only a deliverable (a signed output) gets its manifest embedded, in a new `<name>.signed.v<N>.<ext>`, because platforms and viewers read only what is inside the file. A file that already carries embedded credentials is not signed at ingest: c2patool can only sidecar-sign it against a copy with those credentials stripped, which then does not match the original, and its own credentials are already its provenance. c2patool's ingredient reader ignores sidecars, so the signer attaches an ingredient's sidecar as its manifest store itself; a sidecar-signed WAV keeps its credentials inside the signed output. Measured on a 1.6 GB Pixel take: 14 s, a 13.5 KB sidecar (c2patool writes a temporary copy of the asset, deleted straight away).
