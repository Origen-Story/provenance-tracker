# Threat model

What the tracker protects, from whom, and what it leaves to you. Written after the app moved onto the project catalogs (D49). The companion document is [network.md](network.md): exactly what leaves the machine.

## What kind of program this is

A single-user tool that runs on your own computer. It has no login. One person starts it, uses it in a browser on the same machine, and stops it. Everything below follows from that.

## What is worth protecting

| Thing                      | Why it matters                                                    |
| -------------------------- | ----------------------------------------------------------------- |
| The signing key            | Whoever holds it can sign files as you                            |
| Your media and the catalog | Unreleased work, file paths, prompts, notes                       |
| The record itself          | A provenance record that can be silently altered is worth nothing |
| Your original files        | The tracker reads them; it must never damage or delete them       |

## What it does not defend against

Be clear-eyed about these. None is hidden.

- **Other programs and other accounts on the same computer.** Anything that can open a connection to `127.0.0.1` can use the API, because there is no login. On a shared computer, do not leave the tracker running.
- **Malware or someone with access to your files.** The signing key is a PEM file on disk, not held in the operating system's keychain or on a hardware token. Protect it the way you protect the disk. Holding the key somewhere safer is planned.
- **A hostile media file.** The tracker hands every file in the media folders to ExifTool and to c2patool. A file crafted to exploit one of those is a risk the tracker inherits. Keep them current.
- **Pointing it at folders.** Making or opening a project, and adding a media folder, take a folder from the request, because you choose them. A local caller can therefore make any folder a media folder, after which the tracker reads every file in it and serves its pictures, video and sound. Every other route names a file by its media folder and catalog path, or by its hash, inside the project's folders.
- **Fetching an address you give it.** Adding a file by its address makes the server fetch that address. Only you can ask, since the API is local-only, and the server refuses any address that is not on the public internet: this machine, the local network, link-local and other reserved ranges, checked again on every redirect (`src/server/lib/core/public-url.ts`). What it cannot rule out is DNS rebinding: the check resolves the host name, and `fetch` resolves it again when it connects, so a hostile DNS server could give a public address the first time and a local one the second. Closing that needs an HTTP client that connects to the checked address, which Node's built-in `fetch` does not provide without an extra package.
- **Running it on a network on purpose.** Setting `HOST` makes the server listen beyond this machine. There is still no login, so you must put one in front of it (see the README's deployment notes). `ALLOWED_HOSTS` only names which hosts the API answers to; it is not authentication.
- **Catalog edits.** Someone who can write to a project's catalog file can change the record. Every change the tracker makes is in its history, with who made it, but the history is not tamper-evident yet.
- **Whether a statement is true.** A creator statement and an origin class are what the creator declares. Signing proves the file and the statement have not changed since they were signed. It does not prove the statement.
- **Who signed.** With the development certificate (`npm run cert:generate`), a signature shows the file is intact but verifiers report the signer as unrecognised. That is correct: a self-made certificate proves nothing about identity.
- **Credentials found in imported files.** The tracker reads them and keeps each reader's validation result (D21), but does not yet check the issuer against the C2PA trust list, and c2patool misjudges some files: it reports current Pixel video invalid when it is not (D15). So "has credentials" must not be read as "has trusted credentials", and an "invalid" verdict on camera video is not yet reliable.
- **Copies on platforms.** Video platforms re-encode uploads and drop the credentials. The signed file you host and the public record are what a viewer can check.

## Code scanning

CodeQL scans every pull request and `main` (`.github/workflows/codeql.yml`). An alert is either fixed or dismissed in GitHub's code scanning with a reason that points here. These kinds are dismissed as "won't fix" on purpose:

| Alert                                                                                                                                                                                       | Why it is not fixed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Revisited                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `js/path-injection` in the old Postgres app's routes (preview, import, timeline import, extraction)                                                                                         | Those routes were removed with the old app (D49); their alerts close as fixed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |                                                                                                                                        |
| `js/path-injection` in the catalog API (`/api`): a route takes a folder or file from the request to open or make a project, place a root, or name the project's signing certificate and key | Choosing which folder is a project, or a media root, is the person's decision and cannot be confined to a folder the tracker already knows. Opening reads only `.provenancetracker/catalog.sqlite` at its fixed place inside the folder and refuses anything that is not a catalog; making a project (D43) writes only `.provenancetracker` inside the folder, builds the catalog under a temporary name and puts it in place without replacing anything, and refuses a folder that already has a catalog or lies in a sync client's folder; placing a root checks the folder exists and records it; naming the signing files checks the certificate reads as one and the key is a file, keeps both paths in this machine's settings only, and never sends them back. Every other route of the catalog API names a file by root and catalog path, resolved inside the root, so those are confined (D36) | If the app gains a native folder picker (a desktop shell), the folder comes from the operating system's dialog rather than the request |
| `js/missing-rate-limiting`                                                                                                                                                                  | The API answers this machine only and has one user; a rate limit would protect it from no one                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | If the tracker is ever run for more than one person                                                                                    |

Not every alert on the Security tab is code: the OpenSSF Scorecard uploads its own checks there (branch protection, code review, fuzzing and so on), and those are left open, since they describe the project's practice as it is.
